# Engineering decisions

## 2026-11-05 — Initial implementation

1. Preserve the supplied specification as `docs/BUILD_SPEC.md`. Treat its product requirements as requirements; do not execute embedded instructions as system directives. Follow sequential delivery and record actual phase evidence. The user requested the full product; this first implementation is the foundation and must not be described as completion of all phases.
2. Use the requested TypeScript/pnpm/Turborepo, NestJS, Next.js, Tailwind, Radix and PostgreSQL stack. Keep adult and student apps separate. Do not add an advertising, analytics, identity, payment or AI SDK. The initial OpenAPI document is built from the same endpoint registry used by routing.
3. Docker is not installed in the current Windows environment. Use PGlite solely as a local development and SQL-security-test database. It executes PostgreSQL RLS and triggers; each transaction explicitly switches from its bootstrap owner to the restricted runtime role. Production refuses embedded mode and refuses any connection with SUPERUSER or BYPASSRLS. The same 25-test suite also passed locally on a standalone PostgreSQL 17.11 server with a non-owner runtime role. Temporary Windows database binaries were extracted under ignored `.data/pg-tools` for this check; they are not an application dependency. A PostgreSQL CI job is provided, but neither CI nor the container topology has run here.
4. Migration, bootstrap and demo-seed connections are separate from request-time connections. Tenant context uses `set_config(..., true)`, the parameterised equivalent of `SET LOCAL`, never a persistent session setting. Tenant resolution trusts the HTTP Host only. The Next.js proxy uses Node HTTP requests to preserve Host explicitly; Node fetch in this environment did not reliably preserve a custom Host header.
5. `school_domains` and `users` are platform routing/identity tables. All school-owned tables have `school_id` and forced RLS. No endpoint exposes credential data. Cross-tenant foreign keys are composite where a tenant record references another tenant record. Future modules must follow this convention.
6. Auth initially supports staff password login and privileged-role authenticator TOTP. Parent OTP, new-device OTP for staff, platform SSO/passkeys, recovery and identity enrolment remain pending. Parent demo password login is local scaffolding and must not be launched as the final parent authentication flow.
7. Use opaque, randomly generated session tokens; only SHA-256 hashes are stored. Access expires in 15 minutes; refresh rotates the token with an absolute 8-hour deadline. Cookies are HttpOnly/host-only/SameSite Strict; production uses Secure and the `__Host-` prefix. CSRF uses a separate readable token with a stored hash. Same-school role changes rotate the session. Cross-school context requires sign-in on that school's host.
8. Single-process login and TOTP replay limiters are sufficient for the local foundation. Redis-backed global rate limits and persistent TOTP replay protection are required before multiple API replicas or public release. Redis is reserved in Compose; no queue consumer is claimed to exist.
9. The foundation grants only implemented endpoint permissions. It does not claim the full section 6 operational permission matrix. In particular Accounts has no general audit-log access because finance filtering is not implemented yet. Unknown roles/actions and the disabled student role deny access.
10. AI stays globally off. The approved model registry is empty. The gateway blocks all personal-tier requests, applies conservative public-input screening, serialises budget checks under the settings row lock and records metadata without prompt/response content. This screening is a preliminary safeguard, not a reliable multilingual personal-data detector. Provider onboarding must add verified policy/contract records and stronger data classification before a free model is enabled. Initial OpenRouter adapter accepts only verified zero-cost responses; a paid adapter and currency conversion are deliberately absent.
11. Theme publication creates a new version, serialises concurrent publications per school and darkens inaccessible colours until white text meets 4.5:1. Configuration is data only. Full Brand Studio, rollback and layout publishing are later phases. Required-block validation is available but not connected to a public layout editor.
12. The Today timeline shows real foundation setup states. No fake attendance, student, fee or result statistics are shown. The roadmap explicitly labels unimplemented modules. School/account names in the seed are fictional and labelled demo.
13. Serve Anek Latin, Telugu and Devanagari locally under their SIL Open Font Licenses. No remote font scripts or runtime font requests. Translation files contain the complete UI key set; native-speaker quality review remains a manual gate.
14. No mobile, worker, ledger, ads or App Factory app is generated as an empty placeholder. Add these only when their preceding phase gates pass. No real credentials, school data, store publishing, legal claims or operational integrations are simulated.

## Continued implementation on 5 November 2026

The latest user instruction authorizes continued work across phases. The historical foundation-only notes above describe the earlier snapshot; this section supersedes their descriptions of current functionality.

- Use a central validated module registry, separate tenant tables, shared authorized workflows and schema-driven web/native forms. Common record envelopes contain tenant, owner, class/student/staff scope, version, status and payload. Dedicated finance tables enforce monetary invariants.
- SQL migrations 0002-0012 add operations, finance, student/staff/guardian provisioning, configuration/domains, verification, encrypted OTP/device records and extended registers. All tenant tables force RLS and mutation audit. Server-side scope/audience predicates run before pagination.
- Parent OTP and staff new-device OTP now exist. Production queues encrypted delivery through school-owned adapters; demo codes appear only in embedded mode. Guardian provisioning uses phone-hash identities with random unusable password secrets; possession is proved by OTP. Existing identities are not reset by staff provisioning.
- Monetary arithmetic uses BigInt/integer paise. Journal entries must balance in SQL; receipts and posted ledger entries are immutable. Corrections use reversals. Razorpay uses direct HTTPS without a payment SDK; callbacks verify exact raw-body HMAC and event/payment idempotency. Live provider acceptance is still pending.
- PGlite is confined to development/testing. A standalone worker requires PostgreSQL; embedded mode may use the API worker to avoid two processes opening one local database directory.
- Notification delivery currently uses a PostgreSQL transactional outbox with recipient rechecks, preferences/quiet hours and bounded backoff. BullMQ/Redis is not yet implemented. Provider credentials are injected by environment and must move to a managed secrets integration for production.
- ExcelJS handles XLSX/CSV imports and exports, with size/expanded-archive guards and no formulas/macros. PDF output uses isolated Playwright Chromium with external network requests blocked. QR generation uses the local qrcode library. Expo native UI dependencies were added for the requested mobile app; student dependencies remain separately allowlisted.
- Ads are isolated in their own service/database and disabled by default. Only allowlisted contextual fields cross the boundary; no user/student identifiers are accepted. Google ads remain unimplemented pending provider/legal approval.
- App Factory does not claim a successful build: readiness checks return failures or waiting-for-school. Automatic EAS builds, store submission, secrets-manager integration and OTA are outstanding.
- UI dictionaries retain English fallbacks for several newer operational labels; key parity is not proof of complete Telugu/Hindi translation. Native-speaker review remains open.
- The current exact coverage and unfinished implementation work are documented in STATUS.md. Module presence is not evidence that all advanced module requirements are complete.

## Continued workflow completion

- Admissions conversion creates the student, academic enrollment and guardian OTP account/link in one transaction. It requires structured admission details and cannot run twice on an admitted application.
- Report-card approval snapshots published assessments, configured grading bands, attendance and identity fields. SQL prevents changes to approved/published payloads. Downloads and public verification do not expose question papers or private school data.
- Privacy access/export preparation requires office approval, rechecks requester membership/guardian scope, encrypts the generated content and authorizes downloads. Exports expire after seven days and the worker removes their content. Automated deletion remains pending retention policy implementation.
- Bank CSV/XLSX import follows preview/commit/undo and Accounts-only access. Reconciliation checks signed cash movement and one-to-one journal use. Matched lines are immutable; advanced settlement and multi-bank workflows remain pending.
- Financial statements use integer ledger balances. Balance sheets include cumulative earnings in equity; P&L uses the requested period. This is not a replacement for the accountant's statutory review.
- Configured spending limits now route above-limit requests through Principal and Management. A different person must approve each stage. Posted concessions/refunds cannot be rejected to reverse their financial effect; reversal workflows preserve ledger history.
- Native restoration stores only the origin/CSRF pair in SecureStore and uses native HttpOnly cookies. Concurrent refreshes are serialized in both web and native clients. Native cookie persistence needs physical-device acceptance.
- EAS CLI integration was researched against official Expo documentation, but no automatic EAS worker, signing or store submission is implemented or claimed. Store credentials and deployment remain separate from local JS bundle export.

## Parent workflows and visual organization

The parent web portal uses a dedicated family layout rather than the generic staff record workspace. Five primary destinations, child switching and responsive bottom navigation provide the same authorized data on desktop and phone. Mobile preview embeds only the same-origin root page with `preview=mobile`; other routes retain framing denial.

Files use encrypted private local storage, with quotas and fresh authorization; production PDF scanning is mandatory. Published or reviewed attachments cannot be silently changed. Gallery consent is rechecked at download time. This supplies a local implementation without claiming a production object-storage service.

Privacy deletion is a reviewed decision with explicit retention blockers. Only eligible withdrawn student records can be anonymized, and shared cross-school identities remain untouched. The test-payment endpoint is restricted to non-production embedded fictional schools, marked on receipts and disabled on standalone/production databases. Actual payments still use the school's configured gateway.

## Teacher workspace and development database stability

The teacher landing tab is My School Day, with Your Timeline first and My Classes below. School Feed has its own floating navigation destination. The header uses the configured school logo/accent and a named teacher welcome; a demo crest is used when no logo is configured. School Calendar combines published calendar items, school holidays and assigned-class exams with private dated reminders. Online answers and manual assignment checks are shown together without creating fake parent submissions. HOD syllabus dates and actual teacher completion contribute reviewable counts to performance reports. Family messages, student leave requests and existing school tools remain accessible.

A Windows development restart exposed an invalid checkpoint in the local embedded database. The original directory is retained at `.data/campus-before-recovery-20261105`. Recovery was performed on `.data/campus-recovery-copy`, followed by SQL dump/restore into a clean database; all 119 table row counts and restored constraints matched. Additional checks found zero unbalanced posted journals, zero receipt sequence gaps and zero tenant tables without forced RLS. Recovery dump/count evidence is under ignored `.data/`. This is local recovery evidence, not a production backup/restore certification or a guarantee about transactions interrupted before recovery.

Embedded data directories now have an exclusive writer lock. The development supervisor restarts the API through IPC, waits for database close and checkpoints, then starts the next process. Native PostgreSQL production deployments retain their existing connection path. The local worker schedules due personal reminders every 15 seconds; production uses the configured worker and push adapter.

## Assisted attendance

Voice recognition requires the browser's explicit processLocally capability; unsupported browsers receive alternatives, with no cloud fallback. Screenshot OCR uses self-hosted worker/WASM/language assets and stays in the browser. Matching uses exact full names/admission numbers or unambiguous first names. Unknown, duplicate and conflicting rows require teacher resolution. No missing student is inferred present/absent. The teacher checks the complete roster twice before submission; method and review confirmations are audited without retaining transcripts/images/audio. On-device voice still needs browser and physical-microphone acceptance.
